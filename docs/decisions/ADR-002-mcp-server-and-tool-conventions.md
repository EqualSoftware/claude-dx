# ADR-002: MCP server and tool conventions

- Status: Accepted
- Date: 2026-10-27
- Owners: Maintainer

## Context
The objective of claude-dx is fewer tokens, better quality and the same result each time. Each tool definition and each tool result uses context. Without tools, the model reads a template, lists a directory, finds the next number, writes the file and updates an index. This takes many tool calls and gives different results each time. The server must live for all of a Claude Code session, because it keeps LSP servers warm (ADR-004). The native tools `Read`, `Edit`, `Write`, `Glob` and `Grep` run inside Claude Code. Claude Code checkpoints (`/rewind`) restore only their edits, `Edit` detects stale files, and the permission prompt shows a diff. File operations in Bash (`mv`, `rm`, `cp`, `mkdir`) change between platforms.

## Decision
Server:
- Claude Code starts `claude-dx mcp` as a stdio MCP server from the plugin declaration (ADR-001).
- One server process serves the main session and its subagents.
- The server uses the official Go SDK `github.com/modelcontextprotocol/go-sdk`.
- The server does the background tasks of the session. Example: the update check (ADR-005).

Tool conventions:
- One tool for each operation, with the name `<area>_<verb>`. Examples: `adr_create`, `task_set_status`, `git_commit`.
- Results are compact text for the model, not JSON. A list has one line for each item.
- Errors and messages use ASD-STE100.
- The project root is the git top level (`git rev-parse --show-toplevel`). If the directory is not in a git repository, the root is the current directory. `Project.Resolve` refuses a path outside the project root. The filesystem tools will use it (not built yet). The document tools take slugs and IDs, not paths.
- The launcher passes `--settings` with a permission rule that allows all tools of the server with no prompt (ADR-001). Git tools that change state will ask the user (ADR-003).

Document tools:
- The paths are fixed:
  - ADRs: `docs/decisions/ADR-NNN-<slug>.md`
  - Specs: `docs/specs/<slug>/SPEC.md`
  - Learnings: `docs/learnings/<topic>.md`
  - Glossary: `docs/GLOSSARY.md`
  - Tasks: `tasks/<spec>/<task-slug>.md` in the project data directory (ADR-007, ADR-008)
- A title has 40 characters or less, so file names are short.
- A create tool makes the directory if it does not exist. Other tools do not make directories. If the directory or file does not exist, they return a message, not an error. Example: `No ADRs. docs/decisions does not exist.`
- The binary embeds the templates.
- Tools: `adr_*` (ADR-009 defines the change rules), `spec_*` and `task_*` (ADR-008), `learning_*` (list, get, create, update, delete) and `glossary_*` (lookup, list, upsert, delete).
- Learnings have the frontmatter `topic` and `description`. `learning_create` refuses a topic that exists. The glossary columns are `Term | Definition | Area | Do not use | Source`, and `glossary_lookup` also searches the `Do not use` column.
- The ADR, spec and learning folders each have a generated index `README.md` for persons on GitHub. Its first line is `<!-- Generated by claude-dx. Do not edit. -->`. Each write makes the index again. The model does not read it: it uses `adr_list`, `spec_list` and `learning_list`. The learning tools refuse the topic `readme`. The glossary is one file and it is its own index.

Filesystem tools (not built yet, spec filesystem-tools):
- The tools replace only the shell file operations: `fs_move`, `fs_copy`, `fs_delete`, `fs_mkdir`, `fs_tree` (obeys `.gitignore`).
- They add operations that save tool calls: `fs_read_many` (many files or line ranges in one call), and `fs_move` that updates imports with LSP (ADR-004).
- `Read`, `Edit`, `Write`, `Glob` and `Grep` stay native.
- A `PreToolUse` hook blocks `mv`, `rm`, `cp` and `mkdir` in Bash.

## Alternatives
- A daemon with HTTP transport that the launcher starts: Rejected for now. It can share LSP servers between sessions, but it adds a lifecycle, a port and stale process management.
- `github.com/mark3labs/mcp-go`: Rejected. The official SDK supports stdio and elicitation and has long-term maintenance.
- One tool for each area with an `op` parameter: Rejected. The schemas become unclear and permissions apply to all operations of the area. Claude Code defers MCP tool schemas when there are many tools, so the cost of many tools is small.
- JSON results: Rejected. JSON repeats keys for each item.
- Skills only, with no document tools: Rejected. More tool calls and different results each time.
- No generated index: Rejected. Persons on GitHub lose the overview of the documents.
- Configurable paths: Rejected. Fixed paths are simpler.
- Replace all native file tools: Rejected. Loss of checkpoints, stale file detection, diff prompts and image and PDF reading.

## Consequences
- Positive: simple lifecycle, because Claude Code stops the server when the session stops. Clear schemas, permission for each tool and small results. One tool call for each document change, with the same format each time.
- Negative: two sessions in the same project have two servers and two sets of LSP servers. Many tools, and each tool needs a good description. The templates are fixed in the binary, so a change needs a release. Two sets of file tools when the filesystem tools exist.
- Follow-up: build the filesystem tools (spec filesystem-tools).
